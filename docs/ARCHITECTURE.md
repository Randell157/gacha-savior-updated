# Architecture

How the code works today. `CLAUDE.md` says which section to read for which work.

### Data flow: uploads are parsed in the browser and stored in Firestore

Every data page is a `"use client"` component. The only server code is the username lookup, username change and account deletion routes (see Auth below).

1. The user exports their account as a **GOOD format** JSON file using **Inventory Kamera** or **Irminsul**. Sample exports are in `public/sample-data/inventory-kamera/`: `genshin_export_2026-02-11_12-16.json` (Irminsul, GOOD v3, 1,717 artifacts) and `genshinData_GOOD_2024_10_28_01_22.json` (Inventory Kamera, GOOD v2). The site serves them as static files, which is handy for test uploads. `public/sample-data/test-account/all-characters.json` (from `scripts/build-test-export.mjs`) is made up: every roster character, where some have no weapon, no artifacts, neither, or only some pieces, plus a spare of every weapon and of each set's pieces. Its source isn't Irminsul, so the Obtained sort stays greyed out with it.
2. The Genshin overview (`src/app/genshin/page.tsx`) takes the file from `src/components/UploadArea.tsx`: before the first upload a drag-and-drop `UploadDropZone` with export instructions, afterwards a quiet `UploadBar` (the date of the last upload and an outline "Upload new export" button; it also accepts a dropped file). A green "Saved" alert confirms each upload. The dashboard reads the file and runs **`parseGoodText` / `parseGood`** (`src/lib/genshin/parseGood.ts`). The parser requires `format: "GOOD"`, drops invalid entries and unused fields (returning warnings, which the dashboard shows), turns empty `location` strings into `undefined`, and returns a normalized `GenshinData` in which every list is always present.
3. **`src/lib/genshin/firestoreStore.ts`** saves and loads the upload:
   - `users/{uid}/games/genshin` holds `format`, `version`, `source`, `uploadedAt`, `counts`, `artifactChunkCount`, `characters`, `weapons`, `materials` and `showcase` (5 character keys or null) and `travelerElement` (picked on the Traveler's page, or null).
   - `users/{uid}/games/genshin/artifactChunks/{0..n}` holds `{ items: GoodArtifact[] }`, up to 400 per chunk, because a large export goes past the 1 MiB document limit.
   - `saveGenshin` writes everything in a single `writeBatch` and deletes chunks left over from a bigger earlier upload. `loadGenshin` reads the main document and its chunks, then runs the result back through `parseGood`.
   - Firestore is initialized with `ignoreUndefinedProperties: true`, because the parsed data uses `undefined` for missing optional fields.
4. **`GenshinDataProvider`** (`src/contexts/GenshinDataContext.tsx`) loads the data once per login and shares it with every page. **`useGenshinData()`** (`src/hooks/useGenshinData.ts`) is the only way pages read or write it, and returns `{ data, showcase, setShowcase, travelerElement, setTravelerElement, loading, loadError, lastUploadedAt, migratedFromLocal, save, deleteUpload }`. `save` is async. `setShowcase` and `setTravelerElement` update the screen first and undo the change if the write fails.
5. **Moving data from localStorage:** before Phase 1, uploads lived in `localStorage["genshinData_<uid>"]` (with `genshinShowcase_<uid>`). On login, if the user has no Firestore document and those keys exist, the provider uploads them, deletes the keys, and the Genshin overview shows a "moved to your account" notice.
6. The types live in **`src/lib/genshin/types.ts`** (`GenshinData`, `GoodCharacter`, `GoodWeapon`, `GoodArtifact`, `GoodSubstat`). Import them from there rather than declaring local interfaces.
7. Equipped items are linked to a character by `weapon.location` / `artifact.location` matching `character.key`, not by being nested inside the character. Use **`buildEquipmentIndex(data)`** (`src/lib/genshin/equipment.ts`) to get each character's weapon and artifacts.

The other localStorage keys are `theme` (light, dark or system, written by `next-themes`) and `gachasavior:weapons:view` (Cards or Table). (An older `gachasavior-selected-game` key may still sit in some browsers; nothing reads it now.)

**`useRememberedState(key, initial, scope)`** (`src/hooks/useRememberedState.ts`) is `useState` that survives leaving the page (option "B" from `.mockups/remember-state.html`). The search, sort, show and filter choices on the roster, weapons and artifacts pages use it with its default scope `"tab"`: they stay in `sessionStorage` under `gachasavior:*` until the browser tab closes, and logging out clears them (`clearRememberedTabState`). The addresses stay plain, so a shared link carries no filters. The artifacts page's "Show more" limit isn't kept. It reads during the first render, so use it only behind a loading state, or the prerendered markup won't match.

### Protected pages

`src/components/RequireAuth.tsx` wraps `/dashboard`, `/profile`, `/genshin`, `/genshin/weapons`, `/genshin/weapons/[key]`, `/genshin/artifacts` and `/genshin/characters/[key]`. Given `signedOut`, it shows that to signed-out visitors instead of redirecting: `/genshin/weapons` and `/genshin/artifacts` pass a signed-out version of themselves (the log-in banner, their toolbar faded inside a disabled `<fieldset>`, and an empty dashed box), and `/genshin/characters` shows the banner above the greyed-out roster. The banner is `src/components/SignedOutBanner.tsx` ("You're not logged in.", with Log in and Create account buttons; `EmptyList` is the dashed box), style "A" from `.mockups/signed-out.html`. It shows a loading skeleton (`src/components/PageSkeleton.tsx`, built on the shadcn `Skeleton`) until auth and `useGenshinData()` are both ready. Its `skeleton` prop picks the shape (`dashboard`, `cards` (default), `grid`, `detail`, `rows`) so nothing jumps when the page appears; `/genshin/characters` renders `<PageSkeleton kind="grid" />` itself while loading. It and sends signed-out visitors to `/login` with `router.replace`. Inside it, pages can assume `loading` is false. The pattern is `export default function Page() { return <RequireAuth skeleton="cards"><Content /></RequireAuth>; }`. The `/genshin/characters` roster stays public; signed out, every character shows as unowned. Pressing an unowned tile opens `src/components/CharacterQuickView.tsx` (design "C" from `.mockups/signed-out-character.html`, with the additions from `.mockups/character-hierarchy.html`): a shadcn `Dialog` with the portrait, the game info, talents, base stats and constellations, then a log-in banner, or when signed in a line saying the character isn't in the latest upload. Owned tiles link to the character's page. Closing the dialog puts focus back on the tile that opened it (`onCloseAutoFocus`, since the dialog has no Radix trigger). `/genshin/characters/[key]` itself still sends signed-out visitors to `/login`.

### Auth and Firestore

- `src/lib/firebase.ts` initializes the app from the `NEXT_PUBLIC_FIREBASE_*` environment variables (`.env.local` locally, the Vercel project settings when deployed), sets `browserLocalPersistence`, connects to the emulators when `NEXT_PUBLIC_USE_FIREBASE_EMULATORS=true`, and exports `app`, `db` and `auth`. Each variable must be read as a literal `process.env.NEXT_PUBLIC_...` so Next.js can inline it.
- Collections:
  - `users/{uid}`: `{ username, email, createdAt, avatar, avatarImage }` (`avatar` is the character key chosen as the profile picture, `avatarImage` an uploaded one as a JPEG data URL; at most one is set). `username` is kept as typed, for display.
  - `users/{uid}/games/genshin/...`: see Data flow.
  - `usernames/{lowercased name}`: `{ uid }`, which lets people log in with a username.
- **Security rules live in `firestore.rules`**, and `firebase.json` points the CLI and emulator at it:
  - `users/{uid}` and everything under it: only the owner can read or write. `avatarImage` must be a JPEG data URL of at most 200,000 characters.
  - `usernames`: signed-in users can read; anyone signed in can *create* `{ uid: <own uid> }` only, under a lowercase document ID; nothing can update or delete.
  - Everything else is denied.
  - Test rule changes on the emulator before deploying. The live project only picks up changes once they're deployed. The current file, including the `avatarImage` check, was published on 2026-11-05. The Firebase CLI isn't logged in with an account that can access the project, so publish by pasting the file into the console's Rules tab, or have the user log the CLI in as the project owner first.
- **Username login:** `login/page.tsx` treats any identifier without an `@` as a username and POSTs it to **`/api/auth/resolve-username`** (`src/app/api/auth/resolve-username/route.ts`). The route looks up `usernames/{name.toLowerCase()}`, then `users/{uid}`, using the Admin SDK, and returns `{ email }`. Any failure returns the same 401 "Invalid username or password." Requests are rate-limited in memory to 10 per minute per IP, counted separately on each server instance. The page then signs in with `signInWithEmailAndPassword`. A 401 from the route and Firebase's wrong-credential codes all show the same message ("That email, username or password isn't right..."), so it doesn't reveal which part was wrong. Sign-up shows its own messages for `auth/email-already-in-use`, `auth/invalid-email` and `auth/weak-password` (`SIGN_UP_ERRORS` in `create-account/page.tsx`).
- **Passwords** (option "A" for forgetting and "B" for changing, from `.mockups/password-options.html`). `/forgot-password` (linked from Log in) takes an email or username, looks a username's email up through the same route, and calls `sendPasswordResetEmail`. It shows the same "If that account exists" message for known and unknown accounts. The email and the page its link opens are Firebase's own. The Auth emulator sends no email; its links are listed at `http://127.0.0.1:9099/emulator/v1/projects/demo-gachasavior/oobCodes`, which the `auth` tests read. On Profile, `src/components/ChangePassword.tsx` is the Password row: Change opens a form that re-authenticates with the current password (`reauthenticateWithCredential`), then calls `updatePassword`.
- **Changing a username** (option "A" from `.mockups/change-username.html`). `src/components/ChangeUsername.tsx` is Profile's Username row, posting to **`/api/account/username`**, because the rules don't let the browser delete the old `usernames` document. The route takes the account from the verified token and applies sign-up's rules. In one transaction it claims the new name, refuses it if someone else holds it, deletes the old claim and updates `users/{uid}.username`. Changing only the capitals keeps the same claim. The header updates through `AuthContext`'s listener.
- **Deleting** (option "A" from `.mockups/delete-account.html`). `src/components/DeleteData.tsx` is Profile's Delete data panel, confirming each in a shadcn `Dialog`. Delete upload calls `deleteUpload` from `useGenshinData()` (`deleteGenshin` in `firestoreStore.ts`, a batch from the browser). Delete account re-authenticates with the password, then POSTs to **`/api/account/delete`** with the fresh ID token, because the rules don't let the browser delete a `usernames` document. The route takes the account only from the verified token, refuses a sign-in older than 5 minutes, and deletes `users/{uid}` with everything under it, then the username claim if it's theirs, then the login last, so a failure can be retried. The username is then free for anyone.
- `src/lib/firebaseAdmin.ts` (guarded by `import "server-only"`) initializes `firebase-admin` from `FIREBASE_SERVICE_ACCOUNT_KEY`, which is the service account JSON **base64-encoded** onto one line. In emulator mode it uses no key. It exports `adminDb` (and `adminApp`), and `src/lib/firebaseAdminAuth.ts` exports `adminAuth`; both bypass security rules, so use them only in API routes and scripts. They're separate files so that only the routes needing `adminAuth` load it. `package.json` overrides `jwks-rsa` to 3.2.2 because `firebase-admin/auth` otherwise gets 4.x, which calls `require()` on the ESM-only `jose` 6: that works on Node 24 here, but failed with `ERR_REQUIRE_ESM` on Vercel and made every route importing it return 500. To reproduce that locally, run with `NODE_OPTIONS=--no-experimental-require-module`. Check the override again when updating `firebase-admin`. The downloaded key file (`*-firebase-adminsdk-*.json`) is gitignored. Never print it or the env value.
- **Sign-up** creates the auth user, then claims `usernames/{lowercased name}` and writes `users/{uid}` in a single `runTransaction`. The transaction fails if the name is taken, matching "Zach" against "zach"; in that case the new auth user is deleted. Usernames can't be empty or contain `/` (it isn't allowed in a document ID) or `@` (login would treat the name as an email).
- **`scripts/migrate-usernames.mjs`** renames older `usernames` documents that have capital letters to lowercase. Names that would collide between different accounts are listed and left unchanged. It does a dry run unless given `--apply`, and is safe to run again. It was run on the live project on 2026-11-01, and every `usernames` document is now lowercase. The one conflict (`Randell`, a test account) was resolved by deleting its username document; that account logs in by email.
- **Profile picture** (option "A" from `.mockups/profile-picture.html`). `src/components/ChangePicture.tsx` is Profile's Picture row, writing from the browser, and `src/components/ProfilePicture.tsx` shows the result there and in the header's account button, or the name's first letter if there's none. The picture is either a character (only uploaded ones can be chosen, but it stays if the upload is deleted) or the player's own image (option "A" from `.mockups/picture-upload.html`). A chosen JPG, PNG or WebP, up to 10 MB and at least 128 px on its short side, opens `src/components/PictureCropper.tsx`: a fixed square the image moves and zooms behind (drag, arrow keys, slider), which saves a 256 × 256 JPEG as a data URL in `users/{uid}.avatarImage`. It's in Firestore because Cloud Storage needs a paid plan, and only the crop leaves the browser. The grid is `src/components/CharacterPicker.tsx`, which `ShowcasePicker` wraps with its slots.
- `AuthContext` (`useAuth()`) provides `{ user, username, createdAt, avatar, avatarImage, loading, error }` (`createdAt` is the ISO string from `users/{uid}`, shown on `/profile`). It listens to `users/{uid}` with `onSnapshot`, so the name appears even though sign-up writes the profile just after the account is created.

### Games: the hub and each game's section

Each game has its own section of the site, and `/dashboard` is the hub that lists them.

- **`/dashboard`** (`src/app/dashboard/page.tsx`) is "Your games", where login, sign-up and signed-in visits to `/` land. Genshin Impact is a large card (its app icon, a strip of the user's portraits, last upload, counts, a showcase preview with faint empty squares, option "A" from `.mockups/hub-slots.html`) linking to `/genshin`. Games without a section show as "Coming soon".
- **`/genshin`** is the Genshin section: `/genshin` (overview: the upload bar and the `Genshin` component that used to be the dashboard), `/genshin/characters`, `/genshin/characters/[key]`, `/genshin/weapons`, `/genshin/weapons/[key]` and `/genshin/artifacts`. Every page in it uses `src/components/GenshinShell.tsx`, a `PageShell` with a breadcrumb back to "Your games" and the section's tabs (Overview, Characters, Weapons, Artifacts; a tab stays active on its sub-pages). New Genshin pages go under `src/app/genshin/`, use `GenshinShell`, and get a tab in its `TABS` list.
- The old addresses (`/characters`, `/characters/:key`, `/weapons`, `/artifacts`) redirect permanently to their `/genshin` versions, in `next.config.mjs`.
- `src/lib/games.ts` holds the `GAMES` list (`GameId = "genshin" | "hsr" | "zzz"`): each game's `name`, picker `description`, hub `summary`, `href` and `icon`. Icons are `public/genshinappicon.png`, `starrailappicon.png` and `zzzappicon.png`: 256×256 PNGs with transparent rounded corners, cropped from 1200×630 App Store banners (the 428 px icon at x 386, y 101, corners masked at a 92 px radius, done with `sharp`). `src/components/GameIcon.tsx` shows one at any size (a gamepad if a game has none); the hub cards and the ☰ picker use it. A game without `href` is "Coming soon": greyed out and unclickable in the ☰ picker, and listed under "Coming soon" on the hub. Picking an available game in the ☰ menu opens its section. The picker highlights a game only while you're inside its section (`gameForPath(pathname)`), so nothing is highlighted on the hub; there's no stored "selected game". **To add a game:** build its section under `src/app/<gameId>/` with its own shell and tabs, store its data under `users/{uid}/games/<gameId>` (the Firestore rules already allow it), give it an `href` in `GAMES`, and give it a card on the hub.
- `src/app/layout.tsx` wraps the app as `ThemeProvider > AuthProvider > GenshinDataProvider`.

### Character names and portraits

- `src/lib/genshinCharacters.ts` has `GENSHIN_CHARACTERS`, the full playable roster with portrait filenames and `rarity` (4 or 5, required, as `genshin-db` lists it; the Traveler and the Wonderland Manekin, genshin-db's "Manekin", count as 5). `getCharacterPortrait(key)` gives the portrait path for any roster or GOOD key from the roster's own filename (use it rather than building filenames, which misses names like "AratakiItto"), `getCharacterRarity(key)` looks one up from any GOOD key, and `rarityBackground(rarity)` gives the in-game gradient behind a portrait or weapon icon (gold 5★, purple 4★, blue 3★, green 2★, grey 1★), or a plain tint when unknown. The roster, showcase slots, character page, home page wall and weapon icons all use it. The `/characters` page shows the whole roster, with owned characters (from the upload) marked against unowned ones. Owned tiles add two lines under the name (design "A" from `.mockups/roster-build.html`): "Lv 90 · C2" and the talents as Normal Attack / Skill / Burst ("2/8/10"), with the value being sorted by in bold indigo and a legend above the grid. The roster's order comes from `buildRoster` in `src/lib/genshin/roster.ts`, along with the filters' `matchesCharacterFilters`. Sorting by level, constellation or a talent keeps owned characters first in both directions. **Release** sorts every character by release version (`version` in `characters.json`, A–Z within a version) and **Obtained** sorts owned characters by their position in the upload, unowned after them; each shows its value under the name in bold indigo ("Version 5.3", "#12"). Exports have no dates: Obtained relies on Irminsul listing characters in the order the account got them (seen in its sample export: not ID, release or A–Z order, with the starters first; the user confirmed it matches their account on 2026-11-04), so it's offered only when `source` is "Irminsul" and is a greyed-out menu item for other signed-in uploads, because Inventory Kamera uses the in-game list's order. Above the roster sit a name search, a "Skip to characters" link that only appears on keyboard focus and moves focus to the first tile (option "A" from `.mockups/tab-past-chips.html`), Sort and an All / Owned / Not owned toggle, then `src/components/CharacterFilters.tsx` (designs "B" and "C" from `.mockups/inventory-filters.html`): from the `sm` breakpoint up, Element (in the element chip colours), Weapon and Rarity (gold 5★, purple 4★) as chips and Playstyle and Region as tick-box menus; on phones, a Filters button (with a count) opens all five as labeled chip rows, because the chips pushed the first portrait about 1,000 px down. Element, Weapon and Rarity allow one choice at a time (`SINGLE_CHOICE`; pressing another replaces it, pressing it again clears it), Playstyle and Region choices add up (Support or Healer), and groups narrow each other (and Main DPS), via `matchesCharacterFilters`; the data comes from `characters.json` and `roles.json`, and a character with no region in the game data counts as "Other" (`REGION_OVERRIDES` in `scripts/build-game-data.mjs` fills in the ones the user has picked). "Showing N of 124 characters." appears once anything is filtered, with "Clear filters (N)". Matching uses `normalizeCharacterKey` (lowercase, removes spaces, `_`, `'` and `-`). Any Traveler variant maps to the `traveler` entry.
- Portraits are `public/character-portraits/<Name>_Icon.png` (256×256 PNG), taken from the Genshin fandom wiki, or from the `hoyowiki_icon` link in genshin-db (`images`) for the newest characters. When genshin-db has no `images` yet and the wiki refuses scripts, as with Mitya and Valeriy in 7.2, `https://enka.network/ui/UI_AvatarIcon_<Name>.png` has the same 256 px icon. To replace a portrait, give the new file a new name, like `Vesna_v2_Icon.png`, and update its `iconFile`: `/_next/image` caches by address, so the old picture can keep showing under the same name. **When a new character is released:** add the PNG, add an entry to `GENSHIN_CHARACTERS` with its `rarity` (look it up with `node -e "console.log(require('genshin-db').characters('Name').rarity)"` after updating `genshin-db`), and if the name is two words, add it to `CHARACTER_DISPLAY_NAMES` in `src/lib/utils.ts`.
- **Game data** comes from `genshin-db` (a ~190 MB dev dependency, never imported by the app). `scripts/build-game-data.mjs` (`npm run data:genshin`) extracts what the site needs into committed JSON under `src/data/genshin/`, and reports any set or weapon in the sample exports it couldn't match. It also writes `materialNames.json`, `characterExtras.json` (see the character page below), `characters.json` (each roster character's in-game title, description, element, weapon type, region, affiliation, constellation, release version, birthday and talent names, keyed like the roster; the Traveler has no element or talent names, since the export doesn't say which element, and the Wonderland Manekin has no talent names) and `weaponDetails.json` (each weapon's flavour text, its passive split around the numbers with the numbers for R1 to R5, its second stat's name, and its stat growth: base values, growth curves and ascension bonuses, read from genshin-db's own data file because genshin-db doesn't export them). `src/lib/genshin/characterDetails.ts` reads the first (`getCharacterDetails`, `getCharacterRoles`) and `src/lib/genshin/weaponDetails.ts` the second (`getWeaponPassive(key, refinement)`, `canRefine`, `getWeaponDescription`, `getWeaponStats(key, level, ascension)`, which matches genshin-db's `stats()` at every level checked); only the character and weapon pages import `weaponDetails`, so its size stays out of other pages (the roster's filters and quick view do import `characterDetails`). **Playstyle roles** are hand-written in `src/data/genshin/roles.json` (Main DPS, Sub-DPS, Support, Healer, Shielder), from community consensus and the user's own picks for the 6.x and 7.x characters; not game data, so a new character needs an entry added by hand (ask the user). **Reactions** are hand-written the same way in `src/data/genshin/reactions.json`, with the user's picks and the character quick guides on https://keqingmains.com/q/<name>-quickguide/ as sources (a new character needs an entry; ask the user): each character's list of `{ reaction, note }`, the main one first, read by `getCharacterReactions`; `REACTION_ELEMENTS` in `characterDetails.ts` names each reaction's elements. Stellar Glimmer is a state, not a reaction, so it isn't listed. Two tags sit in the same list: "Generalist" (a grey chip, for characters who don't rely on their own element) and "Swirl support" (Anemo characters who are there to Swirl). Characters in its `elementOnly` list (`isElementOnly`) are best with their own element alone and show a single "Geo only" style chip with no note. Its `travelerReactions` holds one list per Traveler element; the Traveler's page has a dropdown chip where other characters' element chip sits (design "C" from `.mockups/traveler-element.html`; `TRAVELER_ELEMENTS`), and `getCharacterReactions(key, travelerElement)` picks the list. KQM's Anemo, Geo and Electro Traveler guides are at `keqingmains.com/<element>-traveler/`, not under `/q/`. `weapons.json` has each weapon's in-game name, `rarity` (1–5), `type` and release `version`, keyed like the sets; `src/lib/genshin/weapons.ts` reads it: `weaponId(keyOrName)`, `getWeapon(key)`, `weaponHref(key)` (the address of its page), `weaponName(key)` (the in-game name, e.g. "Amos' Bow", falling back to the spaced-out key; use it wherever a weapon name is shown) and `weaponIcon(key)`. `artifactSets.json` has each set's name, release `version` (e.g. "4.3") and 2-piece / 4-piece bonus text, keyed by the name lowercased with everything but letters and digits removed. `src/lib/genshin/artifactSets.ts` reads it: `artifactSetId(keyOrName)` (the shared id), `getArtifactSet(setKey)` for a GOOD set key, `artifactSetName(setKey)` (the in-game name, e.g. "Wanderer's Troupe", falling back to the spaced-out key; use it wherever a set name is shown), `ALL_ARTIFACT_SETS` (every set, newest release first, A–Z within a version), and `activeSets(pieces)` for every set a character has two or more pieces of (largest first). After a game patch: update `genshin-db` (stop the dev server first on Windows), rerun `npm run data:genshin`, then `npm run icons:weapons` and `npm run icons:artifacts`, and commit the JSON and new icons.
- `src/lib/genshin/stats.ts` turns GOOD stat and slot keys into readable text: `formatStatName` ("critDMG_" → "CRIT DMG", "hp_" → "HP%"), `formatStat` (name plus value, with "%" for percentage stats) and `formatSlotName` ("sands" → "Sands of Eon"). Never show a raw GOOD key on a page.
- `src/lib/utils.ts` holds `cn()`, `compareVersions(a, b)` (numeric, so "4.10" sorts after "4.6") and the display-name helpers. `formatKeyWithSpaces` turns PascalCase GOOD keys into spaced words, and `formatMaterialDisplayName` also lowercases minor words ("A Huge Bag of Mora"). Exports drop punctuation, which spacing can't restore, so **`materialName(key)`** in `src/lib/genshin/materials.ts` looks the name up in `src/data/genshin/materialNames.json` first (written by `npm run data:genshin`: every genshin-db material and food name with punctuation, about 13 KB, plus `MATERIAL_NAME_OVERRIDES` in the script for what genshin-db lacks, such as the Mora Pouch; option "B" from `.mockups/material-names.html`), and falls back to `formatMaterialDisplayName`. Use it wherever a material name is shown. About 420 of the Irminsul sample's 1,346 keys aren't in genshin-db (mostly quest items and books); those with punctuation stay wrong until added to the overrides. `formatCharacterIconFilename` turns a GOOD key into its portrait filename.
- **The features content** lives in `src/components/GenshinFeatures.tsx`: `FeatureGrid` (five cards describing what the site does, keep them current when features change, then a dashed "More games soon" card with the planned games' icons in grey) and `SampleDashboard`. The signed-out home page and `/features` both show them; `/features` stays for signed-in users, since the home page sends them to `/dashboard`. **The sample dashboard** renders the real Genshin overview component (`src/components/Genshin.tsx`) with a made-up account from `src/lib/genshin/sampleData.ts` (`SAMPLE_GENSHIN_DATA`, `SAMPLE_SHOWCASE`), so it always matches the dashboard. The component (option "B" from `.mockups/overview.html`) shows everything at once, top to bottom: three small count cards, the showcase, then Top weapons (5★ first, then level and refinement, with icons and holders) beside Materials (the 5 largest stacks). ### UI conventions

The user wants to keep the current look. New pages and features should match it closely, and redesigns need the user's approval first. The full style guidance is in the "UI style" section of `docs/DESIGN.md`.

- **Every page uses `src/components/PageShell.tsx`** rather than placing `<Header />` and `<Footer />` itself:
  - `<PageShell title breadcrumbs? tabs? actions? panel?>`: header, the indigo-to-purple gradient, the white title bar (`breadcrumbs` above the title, `tabs` along its bottom edge, `actions` next to the title, as the sort and filter dropdowns do on `/genshin/characters`), the content panel, and footer. The space above and below the panel is 16 px on phones and 48 px from `sm` up (option "A" from `.mockups/phone-band.html`). `panel` is `"padded"` (default), `"flush"` (no padding, for row layouts) or `"none"` (the page draws its own panels, like `/features`).
  - `<CenteredPage>`: the same frame with content centred, used by login, create-account and the 404 page.
  - `<PageFrame>`: only the header and footer, for full-width layouts. Only the home page uses it: a dark portrait wall hero ("Which of your characters did you actually build?", with "Create an account" and "Try the sample account" buttons), three steps (on slate-900 in dark mode, so they don't blend into the hero, which fades to indigo-950), then "What you can do" (`#features`, the feature cards), "Try it with a sample account" (`#sample`, the sample dashboard) and a "Ready to see your own account?" sign-up band. The wall is pinned to the top of the hero with its natural height and clipped by the section (`absolute inset-x-0 top-0`, not `inset-0`); squeezing it into the hero's height made rows overlap on wide screens. Signed-in visitors are sent to `/dashboard`.
  - All three render through `PageFrame`, which puts a "Skip to content" link first (hidden until it gets keyboard focus) and gives `<main>` `id="main"` and `tabIndex={-1}` so the link can move focus there.
  - `src/components/DetailRows.tsx` (`DetailRows`, `DetailRow`): the label/value rows on About, Contact and Profile. Profile's Last upload row links to the Genshin overview to upload (option "A" from `.mockups/profile.html`).
- **Page titles:** the root layout's title template is `"%s · Gacha Savior"`. Pages are client components and can't export `metadata`, so each route has a small `layout.tsx` beside its `page.tsx` that only sets `metadata.title` (e.g. "Log in"). `src/app/genshin/layout.tsx` sets the template `"%s · Genshin · Gacha Savior"` (its default, "Overview · Genshin", is the overview's title); `genshin/characters/layout.tsx` repeats that template, because a plain string title would stop `[key]` from inheriting it; `genshin/characters/[key]/layout.tsx` uses `generateMetadata` with `formatCharacterDisplayName`. `not-found.tsx` exports its own `metadata`. **A new route gets a `layout.tsx` with its title.**
- **Accessibility (WCAG 2.1 AA, audited 2026-11-02 with axe-core; the main pages have no violations):** small text is at least `text-gray-500 dark:text-slate-400`; `gray-400` / `slate-500` fail contrast. Give a control without visible label text an `aria-label` (the showcase `SelectTrigger`s use "Showcase slot N"; the hidden upload input has one too). Login and sign-up errors are `<p role="alert">`. Error red is `text-red-600 dark:text-red-300` (the login and sign-up errors, and the destructive `Alert`, edited in `src/components/ui/alert.tsx`); shadcn's `--destructive` is only 3.8:1 on white and 1.8:1 on `slate-900`. The `a11y` end-to-end tests check pages with errors on screen, which the first audit missed. Toggles that show or hide text set `aria-expanded` (More / Less on `/genshin/artifacts`). An `overflow-x-auto` area with nothing focusable inside gets `tabIndex={0}`, a role and an `aria-label` so keyboard users can scroll it. Heading levels don't skip: shadcn `CardTitle` is an `h3`, so a page whose cards follow the `h1` directly adds an `sr-only` `h2` (the Genshin overview when `heading={false}`, `/genshin/weapons`). A portrait shown next to the name as text has `alt=""`. Small controls keep their look but get a 44 px tappable area: an `after:absolute after:-inset-*` pseudo-element on the ✕ of `src/components/ui/dialog.tsx` and `sheet.tsx` and on the signed-out theme button, and `h-11` with `-mx-2 px-2` on the header's "Log in". The shadcn `TabsList` text is `text-slate-600 dark:text-muted-foreground` (edited in `src/components/ui/tabs.tsx`), because `muted-foreground` on `muted` is 4.34:1 in light mode.
- **Motion** (the 13 changes in `.mockups/motion-polish.html`, from reviewing the site with the `emil-design-eng` skill; no animation library). `globals.css` has the classes: `press` (anything pressable scales to 0.97 while pressed; the shadcn `Button` has it, and it replaces `transition-colors`; skip it on very wide rows), `fade-up` (new text, given a `key` so it replays), `fade-in` and `wall-in`. `tailwind.config.ts` adds the `ease-out-strong` and `ease-drawer` curves for transitions, and `hoverOnlyWhenSupported`, so `hover:` styles don't stick on touch screens. Keep UI motion under 300 ms, closing faster than opening: the dialog opens in 180 ms and closes in 120 ms, the ☰ sheet takes 280 ms and 200 ms (`.motion-dialog` and `.motion-sheet` at the end of `globals.css`, with a doubled class because `animate-in` and `animate-out` set their own duration). The dialog's `slide-*-1/2` classes aren't a slide: they keep it centered during the animation, which replaces its translate. Arrows turn with `transition-transform duration-150 ease-out-strong motion-reduce:transition-none`. `Segmented` keeps its highlight inside the chosen button and slides it over from the previous one with the Web Animations API. `useFadeAfterLoading(loading)` (`src/hooks/useFadeAfterLoading.ts`, used by `RequireAuth` and the roster) fades `[data-page-content]` in only after a skeleton, so moving between loaded pages stays instant. With "reduce motion" on, a block at the end of `globals.css` leaves only fades, except that the ☰ menu still slides, as the user asked. The user's own Windows has animation effects off, so their browsers report reduce motion. Don't animate keyboard actions, row height or anything seen constantly, such as the 124 roster tiles.
- **Focus rings are indigo.** `--ring` in `globals.css` is indigo-500 in both themes (option "A" from `.mockups/focus-rings.html`; 4.5:1 on white, 4:1 on `slate-900`), which the shadcn controls use, and a base rule gives links without their own ring the same one.
- **Buttons are indigo.** The shadcn `Button` default variant is `bg-indigo-600 hover:bg-indigo-700` (edited in `src/components/ui/button.tsx`), so pages don't set button colours themselves. Its `destructive` variant is `bg-red-600`, because shadcn's `--destructive` is too faint for white text. Use the shadcn `Input` and `Select` rather than native elements.
- **Header** (`src/components/header.tsx`): the "GS" logo (`src/components/Logo.tsx`; `src/app/icon.svg` is the same mark as the favicon) and the name. Features, About and Contact sit in the top bar (signed out, Features goes to `/#features` on the home page; signed in, to `/features`) from the `sm` breakpoint up; on phones they move into the ☰ side menu above the game list. The account menu has Profile, the theme choice and Log out; signed out, a theme icon button sits next to Log in. While auth loads, a grey placeholder shows instead of a "Log in" link.
- **Copy** (reviewed 2026-11-02): sentence case for titles, headings, labels and buttons ("Create account", "Confirm password"); "Log in" / "Log out" as two words for the action; American spelling ("color", "favorite"); "owned", not "obtained"; "and", not "&". "Dashboard" means the "Your games" hub only; call `/genshin` the "Genshin overview". Section titles match their tabs (no "All ..."). Error alerts get a title that says what failed ("Upload failed", "Couldn't load your data") and a message that says what to do next; Firestore and Firebase details go to the console, not the page.
- **Dark mode** (`src/components/ThemeControls.tsx`): `next-themes` puts the `dark` class on `<html>` (Light / Dark / System, default System). Every hard-coded colour class has a `dark:` partner on the same element, following one mapping: `bg-white` → `dark:bg-slate-900`, the gradient → `dark:from-indigo-950 dark:to-purple-950`, `text-indigo-900` → `dark:text-indigo-200`, `text-gray-900/800/700/600/500/400` → `dark:text-slate-100/200/300/400/400/500`, `bg-indigo-50` → `dark:bg-indigo-900/30`, `border-gray-200` → `dark:border-slate-700`. Add the `dark:` partner whenever you add a colour class; shadcn components already follow the theme through the CSS variables in `globals.css`.
- `tailwind.config.ts` also scans `src/lib`, because `rarityBackground` returns class names from there.
- `src/components/ui/` holds generated shadcn/ui components (style "default", base color slate, CSS variables). Add new ones with the shadcn CLI rather than writing them by hand.
- Form fields read through React state have no `name` attribute. Without JavaScript loaded yet, a submit would otherwise put their values, passwords included, in the address and browser history.
- Use the `@/*` import alias for `./src/*`.
- ESLint settings: unused variables are allowed if prefixed with `_`, and `any` is allowed.

### End-to-end tests

Playwright tests live in `e2e/`, with the config in `playwright.config.ts`.

- `npm run test:e2e` (`playwright test`) has Playwright start empty Auth and Firestore emulators (no import or export of `.emulator-data/`) and its own `dev:emu`-style dev server on port 3100, run Chrome headless (`channel: "chrome"`, so no browser download), and stop them all afterwards. Not `firebase emulators:exec`: on Windows it left the Firestore emulator (a `java.exe` on port 8080) running.
- It never reuses a running server, so it can't reach the live project. Stop any dev server and the emulators first, since Next.js allows one `next dev` per folder and the emulator ports must be free.
- A full run takes about 3½ minutes; `npx playwright test e2e/auth.spec.ts` runs one file. The console reporter is `line` (one updating line, with failures printed in full), to keep the output short.
- The servers' own logs are hidden (`stderr: "ignore"`), because the dev server echoes the site's console (including errors the tests trigger on purpose). To see them while debugging, remove that line from the config.
- `e2e/global-setup.ts` refuses to run without the emulators and warms up each route. `e2e/helpers.ts` creates accounts directly through the emulators (`createUser`), logs in (`logIn`, by email; username logins go through the 10-a-minute route) and uploads the Irminsul sample (`uploadSample`).
- The specs: `auth` (sign-up, its errors, login by email and username, the single bad-credentials message, protected-page redirects, forgot and change password, changing a username, deleting an upload or account), `upload` (saved counts, a new upload keeping the Traveler's element, the three upload errors), `pages` (home sample, roster, old-address redirects, character, weapons, weapon, artifacts and profile pages with the sample, including the profile picture) and `a11y` (axe-core, WCAG 2.1 AA, in light and dark mode, including error states and the open quick view).
- Every test makes its own uniquely named user, so they don't depend on each other.
- Failures leave traces and screenshots in `test-results/` and an HTML report in `playwright-report/` (both gitignored; open the report with `npx playwright show-report`).
- There are no unit tests. To check the parser by hand, Node 24 can import the `.ts` file directly: `node --input-type=module -e 'import { parseGoodText } from "./src/lib/genshin/parseGood.ts"; ...'`.
