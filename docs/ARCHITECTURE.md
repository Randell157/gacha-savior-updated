# Architecture

How the code works today. `CLAUDE.md` says which section to read for which work.

### Data flow: uploads are parsed in the browser and stored in Firestore

Every data page is a `"use client"` component. The only server code is the username login, password reset by username, username change and account deletion routes (see Auth below).

1. The user exports their account as a **GOOD format** JSON file using **Inventory Kamera** or **Irminsul**. Sample exports are in `public/sample-data/inventory-kamera/`: `genshin_export_2026-02-11_12-16.json` (Irminsul, GOOD v3, 1,717 artifacts) and `genshinData_GOOD_2024_10_28_01_22.json` (Inventory Kamera, GOOD v2). The site serves them as static files, which is handy for test uploads. `public/sample-data/test-account/all-characters.json` (from `scripts/build-test-export.mjs`) is made up: every roster character, where some have no weapon, no artifacts, neither, or only some pieces, plus a spare of every weapon and of each set's pieces. Its source isn't Irminsul, so the Obtained sort stays greyed out with it.
2. The Genshin overview (`src/app/genshin/page.tsx`) takes the file from `src/components/UploadArea.tsx`: before the first upload a drag-and-drop `UploadDropZone` with export instructions, afterwards a quiet `UploadBar` (the date of the last upload and an outline "Upload new export" button; it also accepts a dropped file). A green "Saved" alert confirms each upload. When an upload replaces an earlier one, the overview runs **`uploadChanges(previous, next)`** (`src/lib/genshin/uploadChanges.ts`) on the data already in the page before saving, and `src/components/UploadChanges.tsx` shows a "Since your last upload" panel below the alert: a tally, new characters with portraits, changed characters (from `buildChanges`, worded by `ShowcaseSlot`'s `changeText`, eight at first with "Show all"), new weapons, weapons no longer there, artifact counts and any characters missing from the new export. GOOD has no artifact ids, so pieces are matched by set, slot, rarity and main stat, first to an identical piece and then to one it could have been leveled into; the previous upload's Traveler takes the new upload's key, since older exports call it `TravelerAnemo` and newer ones `Traveler`. Nothing is stored: the panel shows once, closing it moves focus to `#main`, and a reload or the next upload clears it. When nothing changed, the alert says so instead. The dashboard reads the file and runs **`parseGoodText` / `parseGood`** (`src/lib/genshin/parseGood.ts`). The parser requires `format: "GOOD"`, drops invalid entries and unused fields (returning warnings, which the dashboard shows), turns empty `location` strings into `undefined`, and returns a normalized `GenshinData` in which every list is always present.
3. **`src/lib/genshin/firestoreStore.ts`** saves and loads the upload:
   - `users/{uid}/games/genshin` holds `format`, `version`, `source`, `uploadedAt`, `counts`, `artifactChunkCount`, `characters`, `weapons`, `materials` `showcases` (up to `MAX_SHOWCASES` = 5 of `{ title, picks }`, `picks` being 5 character keys or null; older documents have a single `showcase` array instead, which `loadGenshin` reads as one showcase titled "Showcase"), `previousBuilds` (the previous upload's builds from `snapshotBuilds`, written by `save` from the data being replaced, or null after the first upload), `showcaseOptions` (`{ elementColors, pieceCv }`, both false until turned on), `travelerElement` (picked on the Traveler's page, or null) and `plans` (the Planner tab's saved plans, up to `MAX_PLANS` = 20: `{ kind: "character", key, level, talent }` or `{ kind: "weapon", key, location, level }`, read back through `normalizePlans`; a new upload keeps them, and `savePlans` writes them alone).
   - `users/{uid}/games/genshin/artifactChunks/{0..n}` holds `{ items: GoodArtifact[] }`, up to 400 per chunk, because a large export goes past the 1 MiB document limit.
   - `saveGenshin` writes everything in a single `writeBatch` and deletes chunks left over from a bigger earlier upload. `loadGenshin` reads the main document and its chunks, then runs the result back through `parseGood`.
   - Firestore is initialized with `ignoreUndefinedProperties: true`, because the parsed data uses `undefined` for missing optional fields.
4. **`GenshinDataProvider`** (`src/contexts/GenshinDataContext.tsx`) loads the data once per login and shares it with every page. **`useGenshinData()`** (`src/hooks/useGenshinData.ts`) is the only way pages read or write it, and returns `{ data, showcase, showcases, setShowcases, previousBuilds, showcaseOptions, setShowcaseOptions, travelerElement, setTravelerElement, plans, setPlans, loading, loadError, lastUploadedAt, migratedFromLocal, save, deleteUpload }`. `save` is async. `showcase` is the first showcase's slots, for the Your games card. `setShowcases`, `setShowcaseOptions`, `setTravelerElement` and `setPlans` update the screen first and undo the change if the write fails (`setPlans` also resolves false then, so the page can say so).
5. **Moving data from localStorage:** before Phase 1, uploads lived in `localStorage["genshinData_<uid>"]` (with `genshinShowcase_<uid>`). On login, if the user has no Firestore document and those keys exist, the provider uploads them, deletes the keys, and the Genshin overview shows a "moved to your account" notice.
6. The types live in **`src/lib/genshin/types.ts`** (`GenshinData`, `GoodCharacter`, `GoodWeapon`, `GoodArtifact`, `GoodSubstat`). Import them from there rather than declaring local interfaces.
7. Equipped items are linked to a character by `weapon.location` / `artifact.location` matching `character.key`, not by being nested inside the character. Use **`buildEquipmentIndex(data)`** (`src/lib/genshin/equipment.ts`) to get each character's weapon and artifacts.

The other localStorage keys are `theme` (light, dark or system, written by `next-themes`) and `gachasavior:weapons:view` (Cards or Table). (An older `gachasavior-selected-game` key may still sit in some browsers; nothing reads it now.)

**`useRememberedState(key, initial, scope)`** (`src/hooks/useRememberedState.ts`) is `useState` that survives leaving the page (option "B" from `.mockups/remember-state.html`). The search, sort, show and filter choices on the roster, weapons and artifacts pages use it with its default scope `"tab"`: they stay in `sessionStorage` under `gachasavior:*` until the browser tab closes, and logging out clears them (`clearRememberedTabState`). The addresses stay plain, so a shared link carries no filters. The artifacts page's "Show more" limit isn't kept. It reads during the first render, so use it only behind a loading state, or the prerendered markup won't match.

### Protected pages

`src/components/RequireAuth.tsx` wraps `/dashboard`, `/profile`, `/genshin`, `/genshin/weapons`, `/genshin/weapons/[key]`, `/genshin/artifacts`, `/genshin/wishes` (signed out: a made-up history) and `/genshin/characters/[key]`. Given `signedOut`, it shows that to signed-out visitors instead of redirecting: `/genshin/weapons` and `/genshin/artifacts` pass a signed-out version of themselves (the log-in banner, their toolbar faded inside a disabled `<fieldset>`, and an empty dashed box), and `/genshin/characters` shows the banner above the greyed-out roster. The banner is `src/components/SignedOutBanner.tsx` ("You're not logged in.", with Log in and Create account buttons; `EmptyList` is the dashed box), style "A" from `.mockups/signed-out.html`. It shows a loading skeleton (`src/components/PageSkeleton.tsx`, built on the shadcn `Skeleton`) until auth and `useGenshinData()` are both ready. Its `skeleton` prop picks the shape (`dashboard`, `cards` (default), `grid`, `detail`, `rows`) so nothing jumps when the page appears; `/genshin/characters` renders `<PageSkeleton kind="grid" />` itself while loading. It and sends signed-out visitors to `/login` with `router.replace`. Inside it, pages can assume `loading` is false. The pattern is `export default function Page() { return <RequireAuth skeleton="cards"><Content /></RequireAuth>; }`. The `/genshin/characters` roster stays public; signed out, every character shows as unowned. Pressing an unowned tile opens `src/components/CharacterQuickView.tsx` (design "C" from `.mockups/signed-out-character.html`, with the additions from `.mockups/character-hierarchy.html`): a shadcn `Dialog` with the portrait, the game info, talents, base stats and constellations, then a log-in banner, or when signed in a line saying the character isn't in the latest upload. Owned tiles link to the character's page. Closing the dialog puts focus back on the tile that opened it (`onCloseAutoFocus`, since the dialog has no Radix trigger). `/genshin/characters/[key]` itself still sends signed-out visitors to `/login`.

### Auth and Firestore

- `src/lib/firebase.ts` initializes the app from the `NEXT_PUBLIC_FIREBASE_*` environment variables (`.env.local` locally, the Vercel project settings when deployed), sets `browserLocalPersistence`, connects to the emulators when `NEXT_PUBLIC_USE_FIREBASE_EMULATORS=true`, and exports `app`, `db` and `auth`. Each variable must be read as a literal `process.env.NEXT_PUBLIC_...` so Next.js can inline it.
- Collections:
  - `users/{uid}`: `{ username, email, createdAt, avatar, avatarImage }` (`avatar` is the character key chosen as the profile picture, `avatarImage` an uploaded one as a JPEG data URL; at most one is set). `username` is kept as typed, for display.
  - `users/{uid}/games/genshin/...`: see Data flow; wish history is under `.../genshin/wishes/` (see Wish history).
  - `usernames/{lowercased name}`: `{ uid }`, which lets people log in with a username.
- **Security rules live in `firestore.rules`**, and `firebase.json` points the CLI and emulator at it:
  - `users/{uid}` and everything under it: only the owner can read or write, except that the profile document itself can't be deleted from the browser (the delete-account route does it). `avatarImage` must be a JPEG data URL of at most 200,000 characters.
  - `usernames`: signed-in users can `get` one name at a time (sign-up checks whether a name is free) but can't list the collection. A claim `{ uid: <own uid> }` under a lowercase document ID can only be created at sign-up: the caller's profile must not exist yet and must be created in the same transaction with that username, so each account gets one claim. That's also why the profile can't be deleted from the browser: deleting and re-creating it would allow another claim. Nothing can update or delete a claim.
  - Everything else is denied.
  - Test rule changes on the emulator before deploying. The live project only picks up changes once they're deployed. The current file, with the 1.1 username rules, was published on 2026-11-13. The Firebase CLI isn't logged in with an account that can access the project, so publish by pasting the file into the console's Rules tab, or have the user log the CLI in as the project owner first.
- **Username login** (changed after the 1.1 security audit so an email is never revealed): `login/page.tsx` signs an identifier with an `@` in with `signInWithEmailAndPassword`. Anything else is a username, POSTed with the password to **`/api/auth/username-login`** (`src/app/api/auth/username-login/route.ts`). The route looks up `usernames/{name.toLowerCase()}` with the Admin SDK, takes the email from the Auth user (not the profile's editable copy), checks the password through Firebase Auth's REST API (`callAuthRest` in `src/lib/firebaseAuthRest.ts`), and returns only `{ token }`, a custom token from `adminAuth.createCustomToken`, which the page passes to `signInWithCustomToken`. The email never reaches the browser. A wrong password, unknown name or disabled account all return the same 401. The REST call sends the request's own origin as the `Referer`, because the web API key only accepts the site's addresses (see the key restriction in the Firebase console); against the emulators it goes to `FIREBASE_AUTH_EMULATOR_HOST`. Requests are rate-limited in memory to 10 per minute per IP (`createRateLimit` in `src/lib/rateLimit.ts`, using Vercel's `x-real-ip`), counted separately on each server instance; Firebase also limits failed sign-ins per account. A 401 from the route and Firebase's wrong-credential codes all show the same message ("That email, username or password isn't right..."), so it doesn't reveal which part was wrong. Sign-up shows its own messages for `auth/email-already-in-use`, `auth/invalid-email` and `auth/weak-password` (`SIGN_UP_ERRORS` in `create-account/page.tsx`).
- **Passwords** (option "A" for forgetting and "B" for changing, from `.mockups/password-options.html`). `/forgot-password` (linked from Log in) takes an email or username. An email goes to `sendPasswordResetEmail` in the browser; a username is POSTed to **`/api/auth/reset-password`**, which looks up the Auth user's email on the server and asks Firebase to send the link (REST `sendOobCode`), answering the same `{ ok: true }` whether or not the name exists (rate-limited to 5 a minute per IP). It shows the same "If that account exists" message for known and unknown accounts. The email and the page its link opens are Firebase's own. The Auth emulator sends no email; its links are listed at `http://127.0.0.1:9099/emulator/v1/projects/demo-gachasavior/oobCodes`, which the `auth` tests read. On Profile, `src/components/ChangePassword.tsx` is the Password row: Change opens a form that re-authenticates with the current password (`reauthenticateWithCredential`), then calls `updatePassword`.
- **Changing a username** (option "A" from `.mockups/change-username.html`). `src/components/ChangeUsername.tsx` is Profile's Username row, posting to **`/api/account/username`**, because the rules don't let the browser delete the old `usernames` document. The route takes the account from the verified token and applies sign-up's rules. In one transaction it claims the new name, refuses it if someone else holds it, deletes the old claim and updates `users/{uid}.username`. Changing only the capitals keeps the same claim. The header updates through `AuthContext`'s listener.
- **Deleting** (option "A" from `.mockups/delete-account.html`). `src/components/DeleteData.tsx` is Profile's Delete data panel, confirming each in a shadcn `Dialog`. Delete upload calls `deleteUpload` from `useGenshinData()` (`deleteGenshin` in `firestoreStore.ts`, a batch from the browser); it leaves the wish history, which has its own row, "Delete my wish history", shown once there are saved wishes (option "A" from `.mockups/delete-wishes.html`). Its dialog says how many wishes go and that ones older than six months come back only from the player's own files; it calls `deleteHistory` from `useWishData()`. After either, a status line says what was deleted and takes focus, since the button that was pressed goes away. Delete account re-authenticates with the password, then POSTs to **`/api/account/delete`** with the fresh ID token, because the rules don't let the browser delete a `usernames` document. The route takes the account only from the verified token, refuses a sign-in older than 5 minutes, and deletes `users/{uid}` with everything under it, then every `usernames` claim whose `uid` is theirs (a query, so claims older accounts made outside sign-up go too), then the login last, so a failure can be retried. The username is then free for anyone.
- `src/lib/firebaseAdmin.ts` (guarded by `import "server-only"`) initializes `firebase-admin` from `FIREBASE_SERVICE_ACCOUNT_KEY`, which is the service account JSON **base64-encoded** onto one line. In emulator mode (`usingEmulators()`: `FIRESTORE_EMULATOR_HOST` or `FIREBASE_AUTH_EMULATOR_HOST` set) it uses no key; since the Auth emulator doesn't really check sign-ins, `usingEmulators()` throws when `VERCEL_ENV` is `production`, so the live site can never run that way. It exports `adminDb` (and `adminApp`), and `src/lib/firebaseAdminAuth.ts` exports `adminAuth`; both bypass security rules, so use them only in API routes and scripts. They're separate files so that only the routes needing `adminAuth` load it. `package.json` overrides `jwks-rsa` to 3.2.2 because `firebase-admin/auth` otherwise gets 4.x, which calls `require()` on the ESM-only `jose` 6: that works on Node 24 here, but failed with `ERR_REQUIRE_ESM` on Vercel and made every route importing it return 500. To reproduce that locally, run with `NODE_OPTIONS=--no-experimental-require-module`. Check the override again when updating `firebase-admin`. The downloaded key file (`*-firebase-adminsdk-*.json`) is gitignored, and `.vercelignore` keeps it, `.env*.local` and other local files out of `npx vercel` uploads. Never print it or the env value.
- **Security headers:** `next.config.mjs`'s `headers()` sends `X-Frame-Options: DENY` with `Content-Security-Policy: frame-ancestors 'none'` (no framing), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and a `Permissions-Policy` turning off camera, microphone and location on every page. Vercel adds HSTS. There's no full Content-Security-Policy yet; adding one needs testing against Firebase, Next.js and the build card's image export.
- **Sign-up** creates the auth user, then claims `usernames/{lowercased name}` and writes `users/{uid}` in a single `runTransaction`. The transaction fails if the name is taken, matching "Zach" against "zach"; in that case the new auth user is deleted. Usernames can't be empty or contain `/` (it isn't allowed in a document ID) or `@` (login would treat the name as an email).
- **`scripts/migrate-usernames.mjs`** renames older `usernames` documents that have capital letters to lowercase. Names that would collide between different accounts are listed and left unchanged. It does a dry run unless given `--apply`, and is safe to run again. It was run on the live project on 2026-11-01, and every `usernames` document is now lowercase. The one conflict (`Randell`, a test account) was resolved by deleting its username document; that account logs in by email.
- **Profile picture** (option "A" from `.mockups/profile-picture.html`). `src/components/ChangePicture.tsx` is Profile's Picture row, writing from the browser, and `src/components/ProfilePicture.tsx` shows the result there and in the header's account button, or the name's first letter if there's none. The picture is either a character (only uploaded ones can be chosen, but it stays if the upload is deleted) or the player's own image (option "A" from `.mockups/picture-upload.html`). A chosen JPG, PNG or WebP, up to 10 MB and at least 128 px on its short side, opens `src/components/PictureCropper.tsx`: a fixed square the image moves and zooms behind (drag, arrow keys, slider), which saves a 256 × 256 JPEG as a data URL in `users/{uid}.avatarImage`. It's in Firestore because Cloud Storage needs a paid plan, and only the crop leaves the browser. The grid is `src/components/CharacterPicker.tsx`, which `ShowcasePicker` wraps with its slots.
- `AuthContext` (`useAuth()`) provides `{ user, username, createdAt, avatar, avatarImage, loading, error }` (`createdAt` is the ISO string from `users/{uid}`, shown on `/profile`). It listens to `users/{uid}` with `onSnapshot`, so the name appears even though sign-up writes the profile just after the account is created.

### Games: the hub and each game's section

Each game has its own section of the site, and `/dashboard` is the hub that lists them.

- **`/dashboard`** (`src/app/dashboard/page.tsx`) is "Your games", where login, sign-up and signed-in visits to `/` land. Genshin Impact is a large card (its app icon, a strip of the user's portraits, last upload, counts, a showcase preview with faint empty squares, option "A" from `.mockups/hub-slots.html`) linking to `/genshin`. Games without a section show as "Coming soon".
- **`/genshin`** is the Genshin section: `/genshin` (overview: the upload bar and the `Genshin` component that used to be the dashboard), `/genshin/characters`, `/genshin/characters/[key]`, `/genshin/weapons`, `/genshin/weapons/[key]`, `/genshin/artifacts`, `/genshin/wishes` and `/genshin/planner`. Every page in it uses `src/components/GenshinShell.tsx`, a `PageShell` with a breadcrumb back to "Your games" and the section's tabs (Overview, Characters, Weapons, Artifacts, Wishes, Planner; a tab stays active on its sub-pages). New Genshin pages go under `src/app/genshin/`, use `GenshinShell`, and get a tab in its `TABS` list.
- **The material planner** (option C from `.mockups/planner.html`: on the character and weapon pages and in its own tab; the logic and data are under "Character names and portraits"). `src/components/CharacterPlan.tsx` is a **Plan** section at the bottom of each character page: `CharacterTargets` (`src/components/PlanTargets.tsx`: the target level as a Select of the current level and each cap above it, the three talents as − / + steppers that start at the current levels, and "All to max"), then what's still short and `MaterialList`. "Add to planner" saves it (`upsertPlan`), "Update plan" when the targets differ from the saved ones, and "In your planner" (a link to the tab) when they match. `src/components/WeaponPlan.tsx` is the same on weapon pages, with a level target and, for a weapon you own several of, a Copy choice (each holder, then unequipped copies as one, planned on the highest-level one); it starts on a copy that's in the planner, else one below its cap. **`/genshin/planner`** (`src/app/genshin/planner/page.tsx`) lists the saved plans as cards (portrait or icon, a link to the page, what goes up, "N short" or "Ready", Edit and Remove; a plan whose character or weapon is gone from the upload says so and keeps only Remove), with "Add a character" (`CharacterPicker`) and "Add a weapon" (`src/components/WeaponPicker.tsx`: a searchable list of your weapons, one per holder, every word matching the name or holder), each opening the targets in a dialog; focus goes back to the button that opened it. "Everything still needed" adds the plans up with `combinePlans`, so materials several plans share are compared once with what you have. **`MaterialList`** (`src/components/MaterialList.tsx`) shows a plan as a table (Material, Need, Have, Missing; Have is left out on phones) or as progress bars, picked with a Table / Bars switch remembered on the device (`useMaterialView`, `gachasavior:planner:view`); Each row has the material's icon at 32 px on its rarity color (`RarityIcon`; the 1★ grey when the rarity is null), option "32 px, rarity color" from `.mockups/material-icons.html`: `public/material-icons/<export key>.webp`, 521 of them, 64 px, from `scripts/fetch-material-icons.mjs` (`npm run icons:materials`: every material in `materialCosts.json` plus the EXP books and ore; the icon name comes from genshin-db, or `UI_ItemIcon_<item id>` from its cost lists for materials too new for its material list; Enka.Network first, then Project Amber). In the bars view the numbers drop under the name when the row is narrow. EXP comes first, as "Character EXP" (the Hero's Wit icon) against your books or "Weapon EXP" (Mystic Enhancement Ore) against your ore, then Mora ("Not in your export" for Irminsul files), then the materials still short; ones you already have enough of fold under "Show them". The cost data loads on first use with `useMaterialCosts` (`src/hooks/useMaterialCosts.ts`). Signed out, the tab shows the log-in banner.
- The old addresses (`/characters`, `/characters/:key`, `/weapons`, `/artifacts`) redirect permanently to their `/genshin` versions, in `next.config.mjs`.
- `src/lib/games.ts` holds the `GAMES` list (`GameId = "genshin" | "hsr" | "zzz"`): each game's `name`, picker `description`, hub `summary`, `href` and `icon`. Icons are `public/genshinappicon.png`, `starrailappicon.png` and `zzzappicon.png`: 256×256 PNGs with transparent rounded corners, cropped from 1200×630 App Store banners (the 428 px icon at x 386, y 101, corners masked at a 92 px radius, done with `sharp`). `src/components/GameIcon.tsx` shows one at any size (a gamepad if a game has none); the hub cards and the ☰ picker use it. A game without `href` is "Coming soon": greyed out and unclickable in the ☰ picker, and listed under "Coming soon" on the hub. Picking an available game in the ☰ menu opens its section. The picker highlights a game only while you're inside its section (`gameForPath(pathname)`), so nothing is highlighted on the hub; there's no stored "selected game". **To add a game:** build its section under `src/app/<gameId>/` with its own shell and tabs, store its data under `users/{uid}/games/<gameId>` (the Firestore rules already allow it), give it an `href` in `GAMES`, and give it a card on the hub.
- `src/app/layout.tsx` wraps the app as `ThemeProvider > AuthProvider > GenshinDataProvider > WishDataProvider`.

### Character names and portraits

- `src/lib/genshinCharacters.ts` has `GENSHIN_CHARACTERS`, the full playable roster with portrait filenames and `rarity` (4 or 5, required, as `genshin-db` lists it; the Traveler and the Wonderland Manekin, genshin-db's "Manekin", count as 5). `getCharacterPortrait(key)` gives the portrait path for any roster or GOOD key from the roster's own filename (use it rather than building filenames, which misses names like "AratakiItto"), `getCharacterRarity(key)` looks one up from any GOOD key, and `rarityBackground(rarity)` gives the in-game gradient behind a portrait or weapon icon (gold 5★, purple 4★, blue 3★, green 2★, grey 1★), or a plain tint when unknown. The roster, showcase slots, character page, home page wall and weapon icons all use it. The `/characters` page shows the whole roster, with owned characters (from the upload) marked against unowned ones. Owned tiles add two lines under the name (design "A" from `.mockups/roster-build.html`): "Lv 90 · C2" and the talents as Normal Attack / Skill / Burst ("2/8/10"), with the value being sorted by in bold indigo and a legend above the grid. The roster's order comes from `buildRoster` in `src/lib/genshin/roster.ts`, along with the filters' `matchesCharacterFilters`. Sorting by level, constellation or a talent keeps owned characters first in both directions. **Release** sorts every character by release version (`version` in `characters.json`, A–Z within a version) and **Obtained** sorts owned characters by their position in the upload, unowned after them; each shows its value under the name in bold indigo ("Version 5.3", "#12"). Exports have no dates: Obtained relies on Irminsul listing characters in the order the account got them (seen in its sample export: not ID, release or A–Z order, with the starters first; the user confirmed it matches their account on 2026-11-04), so it's offered only when `source` is "Irminsul" and is a greyed-out menu item for other signed-in uploads, because Inventory Kamera uses the in-game list's order. Above the roster sit a name search, a "Skip to characters" link that only appears on keyboard focus and moves focus to the first tile (option "A" from `.mockups/tab-past-chips.html`), Sort and an All / Owned / Not owned toggle, then `src/components/CharacterFilters.tsx` (designs "B" and "C" from `.mockups/inventory-filters.html`): from the `sm` breakpoint up, Element (in the element chip colours), Weapon and Rarity (gold 5★, purple 4★) as chips and Playstyle and Region as tick-box menus; on phones, a Filters button (with a count) opens all five as labeled chip rows, because the chips pushed the first portrait about 1,000 px down. Element, Weapon and Rarity allow one choice at a time (`SINGLE_CHOICE`; pressing another replaces it, pressing it again clears it), Playstyle and Region choices add up (Support or Healer), and groups narrow each other (and Main DPS), via `matchesCharacterFilters`; the data comes from `characters.json` and `roles.json`, and a character with no region in the game data counts as "Other" (`REGION_OVERRIDES` in `scripts/build-game-data.mjs` fills in the ones the user has picked). "Showing N of 124 characters." appears once anything is filtered, with "Clear filters (N)". Matching uses `normalizeCharacterKey` (lowercase, removes spaces, `_`, `'` and `-`). Any Traveler variant maps to the `traveler` entry.
- Portraits are `public/character-portraits/<Name>_Icon.png` (256×256 PNG), taken from the Genshin fandom wiki, or from the `hoyowiki_icon` link in genshin-db (`images`) for the newest characters. When genshin-db has no `images` yet and the wiki refuses scripts, as with Mitya and Valeriy in 7.2, `https://enka.network/ui/UI_AvatarIcon_<Name>.png` has the same 256 px icon. A paimon.moe pull matches by pool, time, name (letters and digits only) and which of the identical ones it is in that second; when a game export matches one, it takes the game's id. So any mix of paimon.moe and UIGF imports, in any order, gives each pull once.
- **Stats:** `poolStats(pulls, pool)` gives the total, `pity5` and `pity4` (pulls since the last 5★ and the last 4★; a 5★ doesn't reset the 4★ count, because the game holds the 4★ for the next pull), the 4★ count, each 5★ with the pulls it took, and the average per 5★ (pulls up to the last 5★ ÷ 5★s). It's an estimate, since some fates come from Starglitter, events or the shop. `fiftyFiftyRecord(pulls)` counts Character Event `won`, `lost` and `guaranteed` from `poolStats`, with `winRate` = won ÷ (won + lost), null before the first. Checked 2026-11-12 on the user's paimon.moe file: 760,320 Primogems over 4,752 wishes, 18 won and 16 lost.
- **UIGF export:** `toUigf(uid, pulls, { name, version, exportedAt })` writes UIGF v4.2 (`UIGF_VERSION`): `info` with `export_timestamp` in seconds, one `hk4e` account with `timezone` from `uigfTimezone(uid)` (6 → −5 America, 7 → +1 Europe, otherwise +8) and `lang` "en-us" (the names are the site's English ones), and every pull with `uigf_gacha_type` (400 filed under 301), `gacha_type`, `item_id`, `count` "1", `time` as stored, `name`, `item_type`, `rank_type` and `id`. paimon.moe pulls keep their made-up 13-digit ids, which UIGF allows, so a re-import matches them by id and adds nothing.

The export stays out of the repo; paimon.moe's Excel export has no pull or item ids, so it can't be imported as it is.
- **Storage:** `src/lib/genshin/wishStore.ts` keeps wish history apart from the GOOD upload, so replacing or deleting an upload leaves it alone. `users/{uid}/games/genshin/wishes/meta` holds `{ gameUid, lastImportedAt, totals, chunks }` (`totals` and `chunks` per pool), and `wishes/{pool}_{n}` (`character_0`, `weapon_0`, ...) holds `{ items: Pull[] }`, at most `PULLS_PER_CHUNK` (2,000) each. `loadWishes(uid)` reads the meta and the chunks it counts (null before the first import); `saveWishes(uid, gameUid, pulls, previousChunks)` writes a whole, already merged history in one batch and deletes chunks a smaller save no longer needs; `deleteWishes(uid, chunks)` removes it all. ### UI conventions

The user wants to keep the current look. New pages and features should match it closely, and redesigns need the user's approval first. The full style guidance is in the "UI style" section of `docs/DESIGN.md`.

- **Every page uses `src/components/PageShell.tsx`** rather than placing `<Header />` and `<Footer />` itself:

The space above and below the panel is 16 px on phones and 48 px from `sm` up (option "A" from `.mockups/phone-band.html`). `panel` is `"padded"` (default), `"flush"` (no padding, for row layouts) or `"none"` (the page draws its own panels, like `/features`).

The wall is pinned to the top of the hero with its natural height and clipped by the section (`absolute inset-x-0 top-0`, not `inset-0`); squeezing it into the hero's height made rows overlap on wide screens. Signed-in visitors are sent to `/dashboard`.
  - All three render through `PageFrame`, which puts a "Skip to content" link first (hidden until it gets keyboard focus) and gives `<main>` `id="main"` and `tabIndex={-1}` so the link can move focus there.

About and Contact (1.1.1) use `panel="none"` with shadcn cards instead, in the style of the feature cards (option "B" from `.mockups/about-contact.html`); Contact's email has `src/components/CopyButton.tsx`. Error red is `text-red-600 dark:text-red-300` (the login and sign-up errors, and the destructive `Alert`, edited in `src/components/ui/alert.tsx`); shadcn's `--destructive` is only 3.8:1 on white and 1.8:1 on `slate-900`. - **Header** (`src/components/header.tsx`): the "GS" logo (`src/components/Logo.tsx`; `src/app/icon.svg` is the same mark as the favicon) and the name. Features, About and Contact sit in the top bar (signed out, Features goes to `/#features` on the home page; signed in, to `/features`) from the `sm` breakpoint up; on phones they move into the ☰ side menu above the game list. ### Unit tests

Unit tests use Node's built-in test runner (`node:test` and `node:assert/strict`), with no extra packages. Node 24 strips the TypeScript types itself, so the `.ts` files run as they are. The tests sit beside the code they cover, as `*.test.ts`.

- `npm test` runs every `src/**/*.test.ts` in about a second, with no emulators or server. It hides Node's `MODULE_TYPELESS_PACKAGE_JSON` warning: `package.json` has no `"type": "module"`, so Node checks each file's syntax before loading it as an ES module.
- Test files import with the `.ts` extension (`./parseGood.ts`), which Node needs; `tsconfig.json` sets `allowImportingTsExtensions` so `tsc` and the Next.js build accept it. The `@/` alias doesn't work under plain Node, so code under test can only use relative imports (or `import type`, which is stripped).
- Covered so far, in `src/lib/genshin/`: `parseGood.test.ts` (valid exports, rejected files, warnings for skipped entries and unknown versions, optional fields of the wrong type, broken JSON, and all three sample exports in `public/sample-data/`), `artifactScore.test.ts` (Crit Value, the tier edges, unrated, leveling and CRIT circlet pieces, fodder) `stats.test.ts` (stat and slot names, value formatting), `showcaseBuild.test.ts` (main stat names, CRIT from artifacts and the CRIT main stats it can't value, build gaps, changes since the previous upload, Fill's two orders, moving and swapping slots, 5★ +20 main stat values, and the build card's totals), `materialPlanner.test.ts` (saved plans read back, replaced, removed and added up, picking a weapon's copy, the EXP tables against the game's totals, ascensions per level, a full 5★ build, only what's left from 80 and from talent 9, already-ascended characters at a cap, targets below the current levels, matching owned materials by export key, unknown Mora, the Traveler's element, weapons of each rarity), `uploadChanges.test.ts` (the same file twice, new and missing characters, the Traveler's two keys, weapons both ways, leveled, used-up and new artifacts, and the two sample exports) and `wishes.test.ts` (UIGF v4 and v3, multiple UIDs, skipped wishes, other games' files, 19-digit id order, merging overlapping exports, pity, the shared Character Event pity, the 50/50, merging the two test wish exports, splitting into Firestore chunks and reading them back, the paimon.moe Excel import and merging it with game exports in either order, monthly counts, Primogems spent with Beginners' Wish ten-pulls at 8, the 50/50 record, the UID's time zone, and a UIGF download that reads back identical and merges with nothing new) and, in `src/lib/`, `xlsx.test.ts` (reading the test workbook, rejecting non-zip files).

### End-to-end tests

Playwright tests live in `e2e/`, with the config in `playwright.config.ts`.

- `npm run test:e2e` (`playwright test`) has Playwright start empty Auth and Firestore emulators (no import or export of `.emulator-data/`) and its own `dev:emu`-style dev server on port 3100, run Chrome headless (`channel: "chrome"`, so no browser download), and stop them all afterwards. Not `firebase emulators:exec`: on Windows it left the Firestore emulator (a `java.exe` on port 8080) running.
- It never reuses a running server, so it can't reach the live project. Stop any dev server and the emulators first, since Next.js allows one `next dev` per folder and the emulator ports must be free.
- A full run (70 tests) takes about 5½ minutes; `npx playwright test e2e/auth.spec.ts` runs one file. The console reporter is `line` (one updating line, with failures printed in full), to keep the output short.
- The servers' own logs are hidden (`stderr: "ignore"`), because the dev server echoes the site's console (including errors the tests trigger on purpose). To see them while debugging, remove that line from the config.
- `e2e/global-setup.ts` refuses to run without the emulators and warms up each route. `e2e/helpers.ts` creates accounts directly through the emulators (`createUser`), logs in (`logIn`, by email; username logins go through the 10-a-minute route) and uploads the Irminsul sample (`uploadSample`). For rules checks it gets a user's ID token from the Auth emulator (`idTokenFor`) and sends Firestore REST requests as that user or as "owner", which skips the rules (`firestoreAs`, `ownerWrite`).
- The specs: `auth` (sign-up, its errors, login by email and username, the username route never returning the email, the `usernames` rules (no listing, no second claim, no profile delete), the single bad-credentials message, protected-page redirects, forgot and change password, changing a username, deleting an upload or account), `upload` (saved counts, a new upload keeping the Traveler's element, what changed after a second upload, the three upload errors), `planner` (a character's Plan section with raised talents, the Bars switch carried to the tab, adding it and a weapon to the Planner tab, the total, a reload, editing and removing with focus kept; a weapon page's copy choice), `pages` (home sample, roster, old-address redirects, character, weapons, weapon, artifacts and profile pages with the sample, including the profile picture) `wishes` (the signed-out sample; importing `wishes-paimon.xlsx`, then both UIGF test files, with the added counts and a reload; five import errors; deleting the upload keeping wishes, then Profile deleting them; the two-account dialog and refusing another UID) and `a11y` (axe-core, WCAG 2.1 AA, in light and dark mode, including error states, the open quick view, `/genshin/wishes` signed out and before an import, and `/genshin/planner`). The signed-out empty-page test in `pages` includes the Planner tab.
- Every test makes its own uniquely named user, so they don't depend on each other.
- Failures leave traces and screenshots in `test-results/` and an HTML report in `playwright-report/` (both gitignored; open the report with `npx playwright show-report`).
- To check the parser by hand on another file, Node 24 can import the `.ts` file directly: `node --input-type=module -e 'import { parseGoodText } from "./src/lib/genshin/parseGood.ts"; ...'`. Cases worth keeping belong in `parseGood.test.ts` (see "Unit tests").
